# Bilingual / EALD Support Patterns From Richard's Resources

Use this reference when building, reviewing, or adapting bilingual/EALD curriculum supports for Richard, especially English/HASS/Science assessments where a student may think or draft in a home language while the teacher still needs defensible curriculum evidence.

## Core principle

> Use the student's home language to open the curriculum door, then keep the evidence connected to the same curriculum thinking.

Bilingual support is not just a translated worksheet. Richard's stronger resources use home language as an access bridge while preserving the task's cognitive demand, metalanguage, and assessment evidence.

## Pattern observed in Year 9 English/Thai and related files

A strong bilingual assessment support layers:

1. Bilingual task title and instructions.
2. Translated stimulus text or image text.
3. Preserved curriculum verbs and metalanguage in both languages.
4. Glossary / vocabulary bank.
5. Word bank for task-specific analytical language.
6. Sentence starters that launch thinking without writing the whole answer.
7. Step-by-step process guide for the cognitive move (analyse, infer, justify, compare, explain effect).
8. Response boxes that allow home-language or English drafting when appropriate.
9. Read-aloud, autosave, copy/export/print where practical.
10. Teacher-facing mode/report with original response, translation status/field, rubric/criteria, and comments.

## Design rules

- Preserve the original task unless Richard explicitly asks for ICP/adapted level.
- Translate the access layer first: instructions, stimulus text, task verbs, glossary, and key steps.
- Keep hard academic words visible; explain/model them bilingually rather than deleting them.
- Let the student use the language that gives best access to the idea, then support teacher interpretation in English.
- Make machine translation optional and labelled, not the foundation of the support.
- Export the original response as well as any translation; do not treat machine translation as authoritative.
- Separate student support from teacher judgement: calm student view, hidden teacher grading/report view.
- Use bilingual sentence architecture: because/effect frames, evidence frames, audience-response frames, connectives, and own-idea options.
- Maintain student agency: sentence starters should open a response, not make every answer identical.

## Layout and readability pitfalls

- Do not let English and the home language run together in one visual block. Separation is access.
- Prefer stacked paired lines, labelled language blocks, or a clear English / Thai / Both toggle.
- Avoid long bilingual paragraphs when tables, cards, or paired bullets are clearer.
- Keep teacher tools, rubrics, exports, and translation controls visually separate from the student writing flow.
- Collapse glossary/word bank/sentence-starter panels by default if the page becomes dense.

## Technical/privacy cautions

- Build core bilingual support so it works offline/in Edge where possible.
- External Google Translate links can be practical, but label them as internet-dependent and privacy-sensitive.
- Avoid sending sensitive student content to external translation services without explicit teacher judgement/approval.
- Do not rely on Google Fonts or browser auto-translate for the essential student support path.
- If recommending Chrome/Google Translate as an enhancement, make clear that the core file should still function without it.

## Reusable build prompt instinct

When asked to build a bilingual support, first identify:

- What is the original task and year-level demand?
- What cognitive verb/move must the student perform?
- Which stimulus/instructions must be translated for access?
- Which metalanguage must be preserved?
- What sentence frames help the student express the thinking?
- What evidence does the teacher need in original language and English?

Then build the interface around those answers.
